In these rules, "my CLAUDE.md" means my user-level instructions: `~/.claude/CLAUDE.md` and the files it imports. They name my own paths, tools and voice.

Keep a papercut log, shared by all my Claude sessions, of anything that slowed down development, in the file my CLAUDE.md names; if it names none, ask me where before creating one. When you lose time to one mid-session, append a `- ` bullet: date · symptom · fix · project. The gotchas file my CLAUDE.md names holds settled answers by tool; a hook hands a session the matching line when a command or error triggers it. When that file is kept in a repo, commit and push it after a change. Before logging a papercut, grep the gotchas file and the papercut log's open items for an existing entry.

## How I work
- Before implementing against a library, framework, or API, check the version the repo pins and fetch that version's current documentation.
- Give each subagent the cheapest model tier that can do its job, keeping the parent model for judgment.
- Size each task so that one session can finish it, and hand broad searches and long reads to subagents. When a task wraps up, tell me, so I can end the session or `/clear` and start the next task in a fresh session.
- Write a document meant for me to read or work through (call or meeting prep, a brief, a review, a catch-up, a memo) where my CLAUDE.md says such documents go, and give me its link or path; if it says nothing, ask me once. When a project's own rules keep its material off hosted services, write a local file instead and tell me why.
- In repos owned by other people, keep personal notes in `CLAUDE.local.md`, never in files that get committed upstream. Whenever you create a `CLAUDE.local.md` in a repo, check that git ignores it (`git check-ignore -q CLAUDE.local.md`); if it doesn't, add it to the repo's `.git/info/exclude` (`git rev-parse --git-path info/exclude` finds it from a worktree), never to the tracked `.gitignore`.
- A task that may outlive one session keeps a `## Progress` section in `CLAUDE.local.md` at the root of the folder the task runs in: its worktree when the task is in a git repo, or the task's own folder when it has no repo. The section holds what is settled and who settled it, what was tried and why it failed, the questions waiting on me, and, in a repo, the branch state. Update it at each milestone rather than at the end, because the next session started in that folder loads it at start.
- Every session has a stable name, which is also its messaging address where sessions can message each other. A new task starts with the start-task skill, which writes its opening progress record in the task's folder, names the session (`<repo>--<task>` for a task in a repo) and gives the command that launches it from that folder. Any other session is named after its repo or folder, by the launcher my CLAUDE.md names or with `--name`.
- One session works in each checkout. A second session on the same repo gets its own worktree (`claude --worktree <task>`) and a `<repo>--<task>` name. A worktree holds committed files only: commit what the second session needs first, run the repo's setup step in the worktree (such as `uv sync` or `npm install`), and list gitignored files it needs, such as `.env`, in the repo's `.worktreeinclude`.
- Tidy up without asking once a task's work is merged, or once I've dropped it: stop its session, and delete its worktree, its local branch and its remote branch. First check that the worktree has nothing uncommitted or unpushed and, for merged work, that the PR merged at the branch's head. If a check fails, tell me what's left instead of deleting. A task with no repo has no worktree or branches: stop its session and clear its Progress section, and never delete the task's folder.
- To set a secret (a token, password or key), hand me the kit's `kit-secret` command, as its `extras/secrets/README.md` describes. If a secret reaches the chat, tell me to rotate it.

## Verification (everything I build)
- Define done before building: name the checks that will show the change works, and put them in the task's progress record.
- Prefer one end-to-end check that drives the real thing (the app through `/verify`, the API, a live agent session, the pipeline on real input) over more unit tests. Add property tests for invariants and round-trips. When replacing a system, run a differential test with the old system as the oracle, and keep a list of approved differences.
- Each repo has a `repo-checks` skill at `.claude/skills/repo-checks/SKILL.md` that says how to verify a change there end to end. It leaves launching the app to Claude Code's `/run` and `/verify`, with the launch recipe `/run-skill-generator` records. If a repo has none, write it with the `verify-setup` skill and commit it before the first PR.
- Run the repo's checks (tests, lint, build, and the repo-checks skill) before opening a PR, and never open a PR on a failing check. If the repo has no CI, say so in the PR; adding CI is its own task.
- Every PR body ends with a `Verified by:` line naming what ran and what it showed, or `none` with the reason.
- After three failed rounds of fixing the same check, stop and report to me (or the session you report to) with what was tried.
- Don't skip, sleep on or retry a flaky test. Find the cause, or delete the test and record why in the PR.
- Add a rule to a CLAUDE.md, a skill or REVIEW.md only after the same miss shows up in two places, and prune rules that no longer catch anything; `/doctor prompt-audit` finds rules written for an older model.

## Compact Instructions
When compacting, keep the decisions settled with me and who settled them, the approaches tried and why they failed, the branch with its commits and uncommitted files, the questions waiting on me, and the path of any progress record. Drop file contents and command output that can be read again.
